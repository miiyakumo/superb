评估日期：2026-10-23（Asia/Shanghai）。代码基线：`65bf201`；桌面项目版本：`0.2.0`。

本次开始时工作区干净，主题和工作区改动已提交。评估依据为原始需求、当前源码、本轮自动测试及仓库内历史验证记录；本轮没有重新执行真实鼠标、浏览器、屏幕采集或公网模型测试。下文的产品阶段是评估结论，不是发布认证。

## 当前阶段

项目已达到“主要功能闭环、可继续试用打磨”的开发阶段，尚未满足原始需求中的正式发布门槛。当前瓶颈从基础功能开发转向配置可靠性、真实环境验收和长内容性能。不能用已实现条目比例代替安全与平台验收进度。

已经形成的主流程是：采集文字／图片或手动输入 → 内存队列 → 冻结场景、处理规则与接收方 → 本地预处理及外发校验 → 模型流式响应 → 受保护阅读 → 手动复制或可选自动写回。

## 需求需要明确的地方

1. **将“低干扰”拆成可验收的交互约定。** 被动显示、流式更新、翻页和普通按钮保持前台；明确点击文字输入或选字可取得焦点；结束编辑不自动把焦点切回原应用。已有实现基本遵循此约定，应将其作为需求基线，避免后续功能重新引入抢焦点行为。
2. **明确两条采集路径。** 工作区按钮先入队、再发送；一键场景可按配置采集并发送。需要分别呈现接收方、输入范围与动作语义，保留既有授权边界。
3. **区分本地限额与服务能力。** 当前通用新后端默认 200000 tokens、1000000 响应字符；这是客户端默认配置，不证明任意后端都接受这些值。建议把能力信息、用户预算和服务拒绝原因分开表达，保留用户已保存的限额。
4. **冻结首发支持范围。** 先选择明确的 Windows、显示配置、浏览器和采集程序版本完成证据链，其余标为未验证；不要让未冻结的兼容范围无限扩大首版目标。
5. **同步维护需求状态。** `architecture.md` 的 0.1 映射仍写旧输出默认值、“所有 P1 未实现”和早期未执行的 Windows 检查；`p0-workspace.md` 仍记载早期快速连接 token 默认值。保留历史记录，但建立带构建号的当前状态表，避免把历史描述当成当前事实。本报告先补足当前评估入口。

## 优先改进项

以下是后续开发建议；本次只评估和记录，没有修改运行时代码。配置问题来自源码路径检查，尚未进行磁盘故障注入；性能问题是实现层面的风险，尚无性能基准结论。

| 顺序 | 问题及源码依据 | 建议改动 | 完成标准 |
| --- | --- | --- | --- |
| 1 | `MainWindow.xaml.cs` 的 `SaveBackend_Click` 先保存新凭据并替换内存 `config`，再写配置；`Mutate` 还会再次保存。失败路径没有恢复旧内存配置或回收新凭据，旧凭据清理也没有共享引用检查 | 统一配置提交服务：构造并校验候选值 → 写入 → 发布到内存 → 清理不再引用的旧凭据；复用 `QuickSetupPersistence` 已有的事务思路，取消重复写入 | 配置写入失败后旧连接仍可用、内存和磁盘一致、无孤立新凭据；共享引用不被误删；清理失败不会把已保存配置报告成未保存 |
| 2 | `acceptance.md` 的正式采集排除矩阵仍未形成通过记录；最新主题变更未重跑原生矩阵 | 冻结一个候选发布构建，在明确支持的组合上补焦点、保护、锁屏和剪贴板验收；证据绑定提交号、包哈希与环境 | 每个声明支持的组合有步骤、原始证据和结论；未测组合保持未验证 |
| 3 | `Coordinator.Emit` 每个片段执行 `output.ToString()`；`AnswerView.Render` 每次对完整文本调用 `Markdown.Parse`，虽然复用了未改变的 WPF 块 | 先建立长文本基准，再优化快照产生频率、渲染节流及尾部更新；保留跨块引用、未闭合 Markdown 的正确性 | 固定环境下记录 1 万／10 万／100 万字符的分配、UI 延迟、取消响应及滚动稳定性；优化前后可比较，不先宣称已达标 |
| 4 | `MainWindow.xaml` 的预处理设置要求编辑 JSON，错误遮盖范围较难提前发现 | 在受保护窗口加入处理步骤表单、排序、强制／可选标识和处理后预览，发送前显示最终接收方与素材数量 | 用户能验证真正外发的产物；预览失败、强制处理失败均不能绕过策略 |
| 5 | 主窗口同时承担配置、授权、采集、发送和界面协调；历史文档与当前行为已出现偏差 | 按变更需要提取配置提交、工作区编排和授权生命周期服务；给需求、测试、证据建立映射 | 每个服务有清晰状态归属；新改动不需要在多个保存路径重复实现回滚和授权撤销 |

顺序 1 和 2 应作为下一轮发布候选的重点。顺序 3 的收益需要测量确认，顺序 4 直接降低预处理使用门槛；不建议先做大规模架构重写。

## 扩展方向

| 优先级 | 方向 | 用户价值 | 边界与投入判断 |
| --- | --- | --- | --- |
| 高 | 本地 OCR，先支持截图文字提取与人工校正 | 让文字模型处理截图，降低图片输入依赖 | 中等；必须明确本地执行，识别失败可见，先验证语言、布局、耗时和资源占用 |
| 高 | 可视化遮盖与本地敏感字段规则 | 使现有隐私处理能力真正可操作 | 中等；规则结果可预览，强制规则失败阻断，发送产物不带原始附件 |
| 中 | 剪贴板到期清除 | 缩短回答留在系统剪贴板上的时间 | 较小；仅清除仍匹配本应用来源与代次的内容，复用 `ClearOwned` 的归属检查 |
| 中 | 显式开启的短会话上下文 | 支持围绕同一道题或同一段代码继续追问 | 中等；默认单次独立，显示上下文范围和预算；切换后端重新确认；默认仍不保存正文 |
| 中 | 后端能力档案与协议适配层 | 减少参数不兼容，支持更多服务 | 中到较大；先解决已有协议的参数能力和诊断，再按实际需求增加协议；不自动换供应商 |
| 后续 | 多任务排队、定时／变化触发采集、授权备用后端 | 支持重复任务和较长工作流 | 较大；先补目标、时限、频率、预算和停止条件，逐任务冻结授权与接收方 |
| 后续 | 安装包、签名、版本检查与可回退升级 | 降低普通用户安装和更新成本 | 中到较大；保留配置迁移回退、包完整性校验，并明确新增更新网络访问 |

暂不建议把任意 Shell 执行、浏览器操作或全盘搜集并入当前路线。原始需求明确排除了这些范围；若以后需要，应单独定义工具权限、确认机制、参数限制与预算。

## 建议迭代顺序

1. **可靠性收尾：** 统一配置保存事务，完成故障注入回归，校准当前需求映射与版本文档。
2. **发布候选验收：** 固定支持组合，对同一构建执行原生焦点、采集排除、剪贴板与系统会话验收；建立长内容性能基线。
3. **输入体验增强：** 优先可视化预处理与本地 OCR，再增加按需短会话；每项扩展继续通过统一策略入口。

本次不估算工期或总体完成百分比：兼容组合、性能目标和新增功能范围尚未冻结，给出精确数字会掩盖剩余的不确定性。

# AI Coding 协作：连续对话与历史压缩详细设计

设计稿 · 2026-11-07 · 目标代码基线为通用版 `main`（`bb7cca9`）。本文描述待实现行为。

## 1. 使用流程

用户让平台 agent 独立工作，遇到瓶颈时向 Superb 求助。首次提交可以是一段混合文本，从上到下依次是需求、各文件的说明和源码、当前卡点。以后通常只有平台对话、分析、实际编辑的 diff 或测试反馈，也可能只有一句“改完还是同一个错”。

一次点击「发送」产生一轮 Superb 对话。平台 agent 在两次求助之间可以执行任意多步。Superb 原样接收用户转交的记录，模型负责读懂文件、区分计划与实际修改、联系上次回答并提出下一步。程序无需解析 diff、在本地还原项目或要求用户整理固定模板。

首轮需求就是首条用户消息的一部分。后续用户可以补充或修订需求。跨轮记忆来自按顺序发送的完整问答，历史变长后由一段交接摘要接替较早的问答。**本轮输入始终完整进入正式分析。只有此前已经完成的历史可以交给摘要调用。**

## 2. 范围与代码起点

功能由场景 ID `coding` 启用，重命名场景仍可使用。首版覆盖单进程内的一个 Coding 任务，包括剪贴板、截图和混合队列。退出后重新启动会开始新会话。

通用版已有模型连接、可编辑场景提示词、材料队列、流式回答、停止和重答。专用分支 `codex/ai-coding-agent`（`ff8af77`）每轮从需求、文件快照和进度重建结构化请求，并要求模型调用工具提交结果。本设计从通用版的普通 Chat Completions 消息链路扩展，长期保存的基本单位就是用户输入和可见回答。首版只需两类模型请求：日常分析、按需生成摘要。

## 3. 会话数据与请求形状

```csharp
record CodingTurn(long Number, InputSnapshot Input, string Answer);
record ConversationSummary(long ThroughTurn, string Text);
```

`CodingConversation` 持有当前任务 ID、有序的已完成轮次，以及可为空的摘要。轮次从 1 开始编号。`ThroughTurn = k` 表示该摘要已覆盖第 1 至 k 轮。即使摘要内容由用户定制提示词生成，覆盖边界也由程序根据实际送入摘要调用的轮次填写。原始问答在任务存续期间保存在内存中，输入沿用不可变的 `InputSnapshot`，不为每次请求复制所有历史正文。

正式分析使用如下消息序列。方括号中的部分可为空。

```text
system       发送时冻结的 Coding 场景提示词
[user        “此前对话摘要（截至第 k 轮）”和摘要正文]
[user        第 k+1 轮用户输入，保留文字与附件
 assistant   第 k+1 轮 Superb 实际展示的完整回答
 ...]
user         本轮冻结的输入，保留文字与附件
```

首轮直接发送 system 和 user。摘要使用带明确标签的普通消息，避免历史材料获得系统提示词的权限。历史回答保留 assistant 角色；用户贴入的平台 agent 分析、代码块、角色名和 diff 均保留在 user 内容中。首次源码包只在其所属轮次出现一次。历史中只存最终可见回答，不把流式中间片段、思考状态或摘要调用过程当作对话轮次。

## 4. 发送、提交与重答

1. **冻结。** 新发送时固定任务 ID、轮次号、历史版本、输入快照、场景、模型连接及两份提示词。一次「发送」分配一个逻辑轮次，网络重试可产生新的 attempt ID。相同文本经用户再次主动发送，仍是新一轮。
2. **准备。** 校验本轮材料，构造候选消息，运行第 5 节预算算法。需要压缩时先显示“正在整理历史”，沿用同一次用户操作的取消信号。摘要走当前冻结的后端，在内存中收集完整输出。摘要不会显示为正式答案，也不会触发自动复制。
3. **分析。** 使用冻结好的最终消息发起正式请求，沿用当前流式阅读和复制流程。后端收到的本轮文字、附件顺序和内容与用户刚提交的快照一致。
4. **提交。** 仅在正式回答完整、非空，且任务 ID、轮次及操作仍有效时，一次性保存本轮问答和候选摘要。摘要成功后若正式回答失败，可在当前操作的重试快照中复用已生成的摘要。已完成历史的覆盖边界此时仍保持在上次成功提交处。
5. **重答。** 使用该轮第一次正式分析时冻结的消息和目标后端。成功后替换这一轮原有回答；失败或停止时，保留原来已完成的版本。尚未成功过的轮次在首次成功后追加一次。现有「直接回答」重试仍可按其语义调整本次生成参数，输入历史不变；若改动输出预算，重新核验窗口容量。

实现时区分“当前操作”和“正在显示的回答”。`QueueSnapshot` 目前会替换上一题的输入并使当前请求失效。Coding 场景仍然可以清空**本轮草稿**以接收新材料，但已完成轮次存放在会话对象中。历史提交应在协调器确认完成的同一次有效操作中执行一次，避免依赖窗口重绘、剪贴板写入成功或重复的 UI 通知。

## 5. 上下文大小算法

### 5.1 定义可用输入预算

所有数值以 token 或下节规定的 token 估值表示。整数运算向下取整，累计使用 64 位整数。

```text
W       = 当前模型连接的上下文窗口
R       = min(连接的 MaxTokens, 8192, floor(W / 4))
B       = W - R
trigger = floor(B × 80 / 100)
target  = floor(B × 60 / 100)
I       = CountInput(实际准备发送的完整消息序列)
```

`R` 同时作为本次 Coding 正式调用的实际生成上限写入后端相应的 token 参数。这样预留量和发送值一致。普通场景继续按各自的连接参数工作。`W` 来自模型连接的「上下文窗口（tokens）」字段。已知模型可由匹配的连接配置提供值；未知模型或旧配置缺字段时，首版采用 **32,768 的本地预算假设**，在设置中显示“估算，可按服务端实际窗口修改”。它不代表服务商公布的容量。

例：`W = 128000`，`MaxTokens ≥ 8192` 时，`R = 8192`、`B = 119808`、`trigger = 95846`、`target = 71884`。当 `I = 95845` 时可直接发送；当 `I = 95846` 且有可压历史时启动压缩。没有历史的首次输入即使达到 98,000，也可在其他限制通过后直接发送。

### 5.2 CountInput

- **已匹配模型。** 使用与该模型和版本匹配的 tokenizer 及聊天模板，一次编码完整消息序列，包含消息边界、角色、摘要标签和开始生成回答的标记。计数和发送使用同一份消息对象。只有能确定模板时才走此路径。
- **文本兼容端点。** 无匹配计数器时使用固定估式：`I = 32 + Σ(8 + Utf8Bytes(role) + Utf8Bytes(text))`。其中 32 计整次请求开销，8 计每条消息开销。对序列中的每条消息累加，包括系统提示词、摘要和本轮输入。以实际 UTF-8 字节计数，不使用 .NET 的 UTF-16 字符数、HTTP 转义长度或服务端的生成上限。这是可复现的本地预算估值，实际用量由端点决定。首版仅凭此路径即可实现文本工作流。
- **图片。** 有匹配的图像计数规则时，把每张图在该模型上的估值加入消息占用。未知视觉端点无法仅靠尺寸准确计费：以已知文本占用作本地预检，标记计数为“不含未知图像开销”，对整批图片仍执行数量、像素、字节和视觉能力检查，由端点作最终容量校验。收到明确窗口超限时按 5.4 处理。PNG 或 Base64 长度只用于字节限制。
- **字节限制独立检查。** 保留 `Policy.Check` 对当前材料的校验，并把候选历史的文本和图片计入整次请求的内容字节预算。若当前输入可容纳、整段历史导致请求超过配置的 `MaxInputBytes` 或图片总量限制，同样尝试压缩旧轮次。模型 token 窗口和客户端接收材料的大小上限各自生效。

### 5.3 只压历史

1. 先检查「系统提示词 + 本轮输入」能否独立发送。若这一组合已超过硬预算或材料限制，立即指出超限项，保留本轮草稿；发送前可让用户自行拆分。不会截掉包末的测试反馈。
2. 用上次已提交摘要、未覆盖的历史问答和本轮输入组装正式候选。若 `I < trigger` 且其他输入限制通过，直接发送。
3. 若需要压缩，从最早未覆盖的**完整轮次**开始选取连续前缀。优先保留最近两轮；当候选仍超预算时，也允许将其纳入压缩。选择前缀时，可先以目标摘要长度占位，寻找预计能降至 `target` 的最短前缀。例如初始目标长度为 `min(1024, floor(B / 8))` tokens，至少 1 token。该值用于摘要输出限额，最终判断以真实生成文本重新计数。
4. 摘要调用的 system 消息只有**压缩提示词**，输入只有**上一份摘要 + 本批旧问答**。业务系统提示词和本轮新材料均不交给压缩模型。本次输入很短时（例如“同一个错”），保留最近的问答尤其重要。
5. 用候选摘要替换被覆盖的旧前缀，重建正式消息并重新计数。达到 `target` 且其他限制通过即结束。若仍偏大且还有旧轮次，按同样顺序继续吸收旧历史。每次推进覆盖轮次；若已用尽可压轮次、正式消息仍在硬预算内，则直接分析。60% 是目标，80% 是触发点，两者都不阻止一条本身合法的大输入。
6. 已有摘要是剩余的唯一历史且正式消息仍超硬上限时，按剩余空间限额最多精简该摘要一次并重算。仍放不下时提示容量不足，保留草稿和已提交历史，不以空摘要开始另一项任务。

摘要调用也要通过自身预算检查。按同样的消息计数方式计算「压缩提示词 + 上份摘要 + 待压旧轮次」，为摘要输出预留第 3 步的限额。若一批放不下，先处理能放下的较早轮次，然后带上得到的候选摘要处理后续轮次。单个旧轮次太大时可按原文顺序分块整理历史文本，处理完该轮全部块之后才推进覆盖轮次。无法合法提交的单张历史图片或最小文本块会终止整理并说明原因。本轮用户材料不会进入这种分块处理。

### 5.4 服务端与本地估算不一致

通用客户端当前将非成功 HTTP 响应归一为状态码。实现时从有界的错误响应中识别明确的上下文超限代码。普通 HTTP 400、鉴权错误、超时均按原有失败流程处理。只有明确超限、存在可压历史、且能构造比失败请求更短的历史时，才自动整理历史并重试正式请求一次。首轮超限或重试后仍失败，显示调整窗口设置或拆分本轮材料的提示。诊断只记录阶段、估算方式、数量和错误码。

## 6. 两份提示词与设置

| 用户设置 | 存放与生效 |
| --- | --- |
| 场景系统提示词 | 复用 `ScenePreset.SystemPrompt`，新发送时冻结。更新内置 Coding 默认值中“仅依据本次提交”“不自动携带历史”的旧约定。迁移仅替换完全匹配的旧默认文本，自定义文本原样保留，可由用户编辑。 |
| 历史压缩提示词 | 为 Coding 场景增加可选设置，放在高级设置。缺省使用内置文本，可编辑和恢复默认。保存后从下次实际压缩起生效，已有历史及摘要仍然可用。 |
| 上下文窗口 | 放在模型连接高级设置，单位 tokens。保存时校验为可用于上述公式的正整数（至少 4）；空值走 5.1 的本地默认。与现有输出上限分开显示。 |

建议的默认压缩提示词：

> 为接手同一任务的模型写一段简洁的交接笔记。保留当前有效的目标和约束、平台实际做过的修改、已尝试的方案及结果、最后的卡点和待验证的判断。保留有辨识度的文件名、失败用例和必要的报错原文。区分已执行的修改、提出的建议和未经验证的说法。用户后来修正的信息优先。直接输出交接笔记。

沿用既有配置加载、备份和默认提示词迁移流程。旧连接、凭据引用、定制提示词、快捷键继续可用。用户无需填写上下文设置或修改压缩提示词即可开始一个任务。

## 7. 桌面行为与生命周期

| 操作 | 行为 |
| --- | --- |
| 读取剪贴板、截图入队、清空队列 | 操作当前草稿。用户丢弃一张截图、移除材料或替换输入，都不改已完成历史。 |
| 在 Coding 场景发送或「截屏并发送」 | 本次显式发送的材料成为下一条 user 消息，附上同一任务的历史。若使用带截图预览的桌面版本，确认及发送之后才进入会话。 |
| 切到其他场景再切回来 | 已完成的 Coding 对话留在内存。只有冻结的 `SceneId == "coding"` 请求才附带 Coding 历史；其他场景继续单轮工作。当前发送目标按既有的场景及模型选择规则冻结。 |
| 停止整理或生成、超时、后端失败 | 取消当前操作，部分输出可沿用现有展示；任务的已完成轮次与覆盖边界保留。迟到响应通过任务 ID 与现有 generation 检查丢弃。 |
| 「新任务」、紧急暂停、锁屏、保护失效、退出 | 在现有清理入口取消请求，清除 Coding 历史、摘要、重试快照及草稿，使旧操作失效。正常重新选择 Coding 场景可开始新任务。 |

## 9. 验收与实施顺序

先完成连续对话，再加入计数与历史压缩，最后核对桌面入口。在测试中使用可记录请求体的假后端，分别断言正式请求和摘要请求；模型回答质量用同一组三轮材料另行评估。

| 用例 | 可检查的结果 |
| --- | --- |
| 首轮全量 → 第二轮平台 diff → 第三轮“还是同一个报错” | 未压缩时第三次正式请求依序含两次 user 输入、两次对应 assistant 回答及本轮新消息。首轮材料和本次 diff 各出现一次。 |
| 强制在第三轮前触发压缩 | 在本轮材料中放一个唯一标记。所有摘要请求都找不到该标记；正式请求的末条 user 内容与原始输入逐字一致。覆盖轮次连续，近期回答没有重复。 |
| 达到阈值附近及首次大输入 | 使用固定计数器覆盖 `trigger - 1`、`trigger`、`B` 和 `B + 1`。首轮介于阈值和硬上限之间可直接发送；首轮独立超限时既不调用摘要，也不发送截断文本。 |
| 超大旧轮次、多次压缩 | 摘要生成请求本身符合预算；只有完整覆盖的轮次才被替换。确认后续需求修订、失败用例和旧方案的实际结果能通过摘要延续。 |
| 摘要失败、正式回答失败、停止或重答 | 历史不提前增加，覆盖边界不前移。成功重答只替换目标轮次，取消后迟到的响应不会写回。 |
| 场景、截图、配置升级和清理 | 通用问答请求不含 Coding 历史；截图保留为图片，摘要不写入剪贴板；旧配置可打开，自定义提示词保持原值；清空任务后首次请求无旧历史。 |

**人工验收场景。** 首轮源码包含一个失败用例；第二轮用户只带回平台分析和一个 diff；第三轮只贴该用例的新报错。分别在正常窗口和强制压缩条件下运行。读者应能从第三轮回答看出上次实际改了什么、哪种解释已被反馈排除，以及接下来最值得让平台 agent 做什么。协议测试确认消息送对，人工验收确认这段历史对继续工作确有帮助。
